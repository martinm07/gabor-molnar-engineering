## Guidance Document Editor Future Features

- Add button in editor to go to admin view
- Make the current .doc not the container, and instead part of the document, so that max-width and stuff can be modified.
- Add ability to modify pseudo classes of elements directly on the element. Can't be done by modifying style attribute. Perhaps using custom data- attributes?
- Add full stylesheet editor, or maybe just reuse the CSS editor but for "elements" where their "names" are CSS selectors. I like that because I can fit it in the sidebar (and it uses what I already have).
- Make document of ID 1 not require admin authentication, so others can still access my editor.
- Make adding nodes by wrapping other nodes also go to "chooser" where you can select a component.
- Add ability to Shift-click to select all nodes between two nodes.
- Revamp the potential locations choosing (for adding and moving nodes) to have two "sub-modes"; adding/moving as child, and adding/moving as sibling.
- Add context-aware keybinds listing in the bottom-left box on the screen.
- Add media-type components? Or otherwise allow media files in the component library (then presumably inherited by the media trays of documents, in a separate listing).
- FIX THAT GOSH DARN SELECTION VISUAL DISAPPEARING (requiring a reload to fix).
- Add style-type components, which are collections of CSS rules (selectors and applying styles). We could also make a style component represent a _single_ CSS rule, but that's not the level I want these components to operate that (they should implement whole themes, or layouts, in my mind).
- Allow precedence configuration for style components added to a document? For example  you have a "sci-fi theme" component, bit want to apply a "mediaeval quotes" style component, that specifically styles &lt;quote&gt; elements to look mediaeval or something, idk haha. This is just considering how one may modularise style components such that one may want to apply more than one to a document. Probably overkill. Will reconsider later.
- Allow components to refer to other components in their definition. This would be cool but seems tricky. When editing the component library and you edit a component, the expectation is that those changes are immediately reflected in the components that refer to it. And that updates work in a similar way to how they do when documents update their component library version. This basically requires implementing a reactivity system, where components make externally available the list of components they refer to, so that they can be informed of updates. And when they update they each inform the components that refer to them about those updates, etc. and this continues until all updates have propagated. I would have to address circular dependencies as well as performance concerns for large libraries (eventually).
- Visually disable components that can't be added to the current component when adding a node to a component (if implementing the above, that would be components that refer to it already, to avoid circular dependencies. If not implementing, then that's _all_ components, which is how it is currently, it's just not visually shown).
- Add colour palette components- each one just defines a list of colours, and would integrate with...
- ...Implement a custom colour picker. The original idea was to use Floating UI, and a keybind to being it up under your cursor whenever you're typing. Maybe that's unnecessary- it could also be a pop up like the media tray, with a button in the top bar.
- Have the colour palette component associate CSS variable names with different colours.
- Implement parsing/syntax highlighting/autocompletion for CSS values. This also sounds rather complicated (perhaps I'd implement a language server protocol?).
- Add button to turn element into component.
- Add button to break inheritance of component.
- In general, make sure the "upgrade library logic" is good. Right now it feels brittle to me. Also fix the editing of "data-comp" and saving new values (that broke a while ago). Though that feature in particular is quite useless I feel.
- Implement the ability for making interactive components (a new component type, like "svelte type" or something). This component would just literally implement a Svelte component, and be edited using a proper in-browser IDE (some vscode fork or something- I remember looking into options before and there being some good ones). Alternatively I can also just link to the Svelte playground. Or maybe embed the Svelte playground! I believe it's open source. How these would be rendered would be tricky. Perhaps I make them compile to custom HTML elements? I'd have to look into that further.
- The ability to copy and paste elements. And/or to duplicate elements (up or down).
- Some way to convert markdown into HTML and vice-versa? I imagine a special .md-container element and a button in the topbar (of a keybind) that automatically converts it to HTML, and then a keybind which can convert HTML into markdown inside a .md-container element.
- Also maths. Rendering math equations. This could be a custom component in the component library (a Svelte component), which shows the LaTeX and a preview render on the bottom, in development mode, and when published it just shows the render.
- The above two ideas should be things that are possible with "svelte-type components", should we implement that. Svelte-type components should be able to know if they're in a development or published environment, and they should be able to use special classes like "not-body", so undo/redo, the potential-location system, and docsyncing don't freak out when the changing LaTeX is continually destroying and recreating all the little elements that MathJax uses in the render, for example. However, if we don't implement that then math equations at least should have this custom component built-in, as it's such a common requirement.
- Math equations should also be integrated with document importing.

- Macros. A "macro-type" component, whose body is a JavaScript script which assigns some global variables (like whether it appears in the topbar, at what position, what phosphor icon or otherwise it should have, what keybind activates it, etc.) and defines one (maybe more) hooks, which are functions that execute based on the defined conditions (in the global variables). These hooks should usually be fairly simple, and interact with the editor's API (which yes, would also need to be made). This would be stuff like "wrap the current selection in a component" or unwrap the current selection if it's this component (removing that component).  I mean frankly, that's the main thing, and maybe we don't need to implement full JavaScript scripting at all. This should allow stuff like "italicize the text", "convert the HTML to a markdown component", etc.
- This also got me thinking further about how you'd interact with Svelte-type components in general. I don't want to implement some complex system for these components to define sidebar UI where they accept inputs. Instead, I think we can just interact by editing the body elements they insert into the document, which the Svelte components uses in whatever it "renders" in published mode. Like a carousel that allows you to insert image elements into a development-only "tray", that disappears in the published document. Or maybe you edit a data-attribute to specify filename globbing for all images in the media tray that it should include.
- I've also looked further into Svelte editors and compiling Svelte code. It definitely seems possible. Import the svelte package as a runtime dependency and use compile() from svelte/compiler. This function accepts CompilerOptions and one of them is absolutely rendering to a custom element. However, that turns out to not be what I really want. The question of "how do I save interactive svelte components inserted into documents, which are just saved as basic HTML strings" may be to just store placeholders that an extra script hydrates (loaded alongside the document, versioned to the component library). The editor will have compiled and mounted svelte components, so docsyncing would need extra logic to recognise where these live and only save the placeholder. Loading docs for editing would require hydrating the placeholders as well, but this could probably be done dynamically and client side (since we'll be implementing a Svelte editor anyway). The hydrator script needs to identify placeholders with svelte-type components in the library (versioned). The raw Svelte code is what's stored in the database, and needs to be compiled at some point. Doing this on the client for readers would be too much of a performance hit, but is the only place with the appropriate environment. So likely do have to do it there (definitely can't do it on the Python server. I mean technically it is possible but we're too resource constrained already to start downloading a Node.js runtime, etc.). Then we populate a cache database from the client's work. Making clients download (request) the Svelte compiler is also a lot... It should be possible it only request dynamically based on if there have been cache misses.
  
  Also, the very cool esm.sh is a CDN that does bundling and resolution into ESM modules, allowing the use of any npm packages in our user written svelte-type components, hopefully (even when they use CommonJS bundling, or any host of other problems that occur with a pure file server like JSDeliver). Weirdly, the Svelte playground seems to build in such a way where it doesn't respect import statement URLs and transforms them in a way that can break them (like absolute path imports from a URL import, typically the browser treats those absolute paths as coming from the same URL root as the initial import statement itself, which esm.sh relies upon). This means users can create components with external dependencies, and we don't need to package in a whole bundler along with the Svelte compiler.

- Disallow moving of component children. Only allow moving of the component as a whole.
- Add button to preview documents (as it would be seen by readers).
- Integrate undo/redo into the editor further, recovering caret position, selection, etc.

- Implement the document hierarchy view. This just reflects the nodes that are in the document, like what you see in devtools. Sections could be collapsible, clicking on nodes scrolls to them and selects them. Nodes could give given special names (using a data- attribute).
- The document hierarchy view should also reflect the ability to do operations like adding nodes and moving nodes. Potential-locations are created in the hierarchy view just like they are in the document itself, and can be interacted with in the same way.

- Allow multiple different component libraries. Which one is used by a document should be able to be chosen within the document. Perhaps at first there is no library chosen. Creating new component libraries should also be possible. A separate view should probably be used where deleting component libraries can be allowed (since it is such a dangerous operation).
